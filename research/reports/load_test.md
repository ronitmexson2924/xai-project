# Load test (R7)

> Generated by `research/load_test.py`. **Do not edit by hand**: rerun it.

- 100 concurrent simulated learners, 10 learning steps each. Each step is three requests, each with its own session and commit: next step (state + planner + style + store explanation), the attempt, and the explanation feedback (a background task in the API).
- One Python process, 100 threads (FastAPI runs sync endpoints in a thread pool); connection pool 20 + 20 overflow; Postgres 16 on the same machine. Times are measured in-process (service code + database, no HTTP/JSON).
- **Paced** is the acceptance scenario. Real learners spend about a minute per step reading and answering, so 100 of them send about 4 requests/s. The paced test's 2 s think time is about 12x faster than that.
- **Burst** removes think time entirely. It finds the point where one process saturates, not a realistic load.

## Reading the burst result

Uncontended, every operation takes about 5-10 ms. One process is CPU-bound by Python's GIL at roughly 130-150 requests/s. In the burst scenario, 100 simultaneous requests queue behind each other (latency ≈ concurrency / throughput). The extreme tail comes almost entirely from the synchronized cold start (every learner's first request in the same instant, while the connection pool is still being built); steady state stays near the budget even with no think time at all. Deploy with several worker processes (e.g. `uvicorn --workers 4`) to raise the ceiling; nothing in the services keeps per-process state that would prevent that.
